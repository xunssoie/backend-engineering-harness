## Phase 4. 결함 재현

### 목적
아무 제어도 없는 원본 상태(`-0`)에서 불변식이 실제로 깨지는 것을 관측한다.
이 측정이 모든 후보의 비교 기준이 된다.

**게이트.** 위반이 관측되지 않으면 Phase 5로 넘어가지 마라.
재현하지 못한 결함은 고쳤는지도 확인할 수 없다.

### 선행 조건
- Phase 3 완료
- 애플리케이션이 **아무 동시성 제어도 적용하지 않은 원본 코드**로 기동되어 있다
- `git status`가 깨끗하다 (후보 코드가 섞여 있으면 `-0`이 원본이 아니게 된다)

### 참조 파일
- `.claude/skills/fix-concurrency/template/measure.sh` (머리말에 순서와 산출물)
- 주입된 `stack`의 **측정 구간 락 카운터**, **최근 데드락 원문** 절

### 절차

1. 아래 명령을 호출자에게 제시하고 끝났다는 답을 받는다. **실행은 호출자가 한다.**

   ```bash
   bash .claude/skills/fix-concurrency/template/measure.sh {이슈번호} {슬러그} 0
   ```

   `measure.sh`가 되돌리기(`reset_ok` 확인) → 락 카운터 BEFORE → 폭발 부하(+ 대기 락 표본) →
   락 카운터 AFTER와 데드락 원문 → 불변식 검증을 한 번에 하고, 원본을 대상 디렉토리에 남긴다.

   - **워밍업을 돌리지 마라.** 폭발 부하는 한 번만 터뜨린다. 워밍업이 상한을 채워버린다.
   - `!! reset_ok가 1이 아니다`로 멈췄으면 데이터가 초기 상태가 아니다. 원인을 짚고 다시 돌린다.
   - 같은 `n`의 파일이 있어 멈췄으면, 앞 측정이 무효인지 호출자에게 확인한 뒤에만 `FORCE=1`을 붙인다.

2. 실행이 끝나면 원본을 가공한다. 터미널 출력을 붙여넣게 하지 마라.

   ```bash
   harness conc-burst-summary {대상 디렉토리}/k6-burst-raw-0.json --out {대상 디렉토리}/k6-burst-summary-0.json
   harness conc-lock-delta {대상 디렉토리}/lock-stats-0.txt
   harness conc-compare {대상 디렉토리}
   ```

   | 산출물 | 파일 | 읽는 법 |
   |---|---|---|
   | 불변식 검증 | `invariant-0.txt` | Read (원본), `conc-compare`의 `violations` |
   | k6 요약 | `k6-burst-summary-0.json` | `conc-burst-summary` 출력 |
   | 락 지표 | `lock-stats-0.txt` | `conc-lock-delta`의 `metrics`. 데드락이 있으면 `LATEST DEADLOCK` 구간만 Read |

   - 락 카운터는 전역 누적값이다. 증가분은 `conc-lock-delta`가 BEFORE와 AFTER의 차이로 낸다.
   - `deadlockTextPresent`가 true인데 `deadlocks` 증가분이 0이면 그 원문은 이번 구간의 것이 아니다.
   - `notes`가 있으면 해석 전에 확인한다(꺼진 지표, 구간 값이 아닌 지표).

3. **재현 여부를 먼저 판정한다.** 이 판정이 게이트다.

   | 조건 | 판정 |
   |---|---|
   | `violations`가 하나라도 0이 아님 | **재현됨.** Phase 5로 간다 |
   | 전부 0인데 요청이 대부분 실패 | **재현 실패.** 요청이 경합 지점에 도달하지 못했다 |
   | 전부 0이고 요청도 정상 | **재현 실패.** 경합이 약하다 |

   재현에 실패했으면 원인을 아래 순서로 짚고 Phase 3으로 돌아간다.

   - 응답 분포(`outcome`)를 먼저 본다. 성공 수가 허용 상한보다 한참 적으면 다른 검증에 걸린 것이다
     (중복 요청, 사용자별 한도, 상태). Phase 3-A의 2번 표를 다시 확인한다
   - 되돌리기가 실제로 됐는지 본다. `conc-lock-delta`의 `reset`이 초기 상태와 다르면 그것이 원인이다
   - 위 둘이 아니면 VU를 올리거나 허용 상한을 낮춰 경합을 세게 만든다
   - **위반이 안 나온다고 "문제가 없다"고 결론짓지 마라.** 재현 조건을 못 만든 것과 결함이 없는 것은 다르다.
     세 번 이상 조건을 바꿔도 재현되지 않으면 그 사실을 호출자에게 보고하고 판단을 받는다
   - 구조적으로 깨질 수 없는 불변식(예: 감소 단독 부하에서 집계가 실제보다 크게만 남는 경우의 하한)은
     0이 정상이다. 그 불변식은 회귀 방지용으로 남긴다. **0이라고 결함이 없는 것이 아니다.**

4. 관측 자료를 표로 정리해 제시하고, **해석은 호출자에게 묻는다.** `SKILL.md`의 **분석 주도 규칙**을 따른다.

   **정합성 (1급)**

   | 불변식 | 기대 | 실측 | 위반 |
   |---|---|---|---|

   **응답 분포**

   | 구분 | 건수 | 의미 |
   |---|---|---|

   **경합 (2급)** (`conc-lock-delta`의 `metrics`)

   | 지표 | 증가분 |
   |---|---|

   - 물을 것: "이 수치가 나오려면 요청들이 어떤 순서로 겹쳐야 했을까요?"
   - 특히 **카운터 정합 오차**를 짚어 묻는다. 이 값이 lost update의 직접 증거다.
     점유 행은 N개인데 카운터가 1이면, N개의 트랜잭션이 같은 값을 읽고 같은 값을 썼다는 뜻이다.
   - 응답이 전부 2xx인데 오차가 크면 그 사실을 짚는다. **애플리케이션은 아무 이상도 감지하지 못했다.**
   - 락 대기가 높은데 오차도 크면 짚는다. 쓰기는 직렬화됐지만 읽은 값이 낡았다는 뜻이다.
   - 호출자가 답하기 어려워하면 그때 인터리빙을 시간순 표로 그려 보여준다. 각 단계에 근거가 된 수치를 붙인다.

5. 결과를 `record.md`의 **재현 (Baseline)**에 채운다. 원본 수치를 옮겨 적지 말고 판정과 근거만 적는다.
   진행 상태를 갱신한다.

   ```bash
   harness conc-progress {record.md 경로} --phase 4 --mark ✅
   ```

### 출력
- `invariant-0.txt`, `k6-burst-raw-0.json`, `lock-stats-0.txt` (호출자), `k6-burst-summary-0.json` (스킬) 생성
- `record.md`의 **재현 (Baseline)**에 불변식별 위반 건수, 응답 분포, 락 지표, 진단이 기록
- 진행 상태의 Phase 4가 ✅

### 실패 처리
- 요청 실패율이 높아 경합 지점에 도달하지 못했으면 **수치를 해석하지 말고** 원인부터 보고한다.
- 애플리케이션이 부하 중 죽었으면 그 사실과 로그를 먼저 보고한다. 부분 결과로 판정하지 마라.
- 재현에 실패해 다시 재야 하면, 실패한 `-0` 파일은 호출자 확인 뒤 지우거나 `FORCE=1`로 덮는다. 기록에는 실패 사실을 남긴다.

> 다음 Phase 조건: 불변식 위반이 관측되어 `record.md`에 기록되었을 때 → Phase 5

> 재현 실패 시 → Phase 3 (경합 조건을 다시 잡는다)

> Skip 조건: 없음 (필수 Phase)
