# 시드 모듈 작성 규칙

성능 측정용 더미 데이터를 도메인 단위 모듈로 만들어 이슈를 넘어 재사용하는 방법이다.
모듈은 프로젝트의 것이다. 이 디렉토리가 아니라 `perf.seedsDir`(기본 `.claude/resources/perf/seeds/`)에 둔다.
**규모와 카디널리티는 변수로만 정한다.** 한 번 만든 모듈의 본문은 이슈마다 고치지 않는다.
DB별 문법과 함정(변수 문법, 행 생성, 중복 가드, 필수 컬럼 조회)은 `stacks/{perf.db}.md`의 **시드** 절에 있다.

## 구성

```
.claude/resources/perf/
├── seeds/                      # 프로젝트 시드 모듈 (perf.seedsDir)
│   ├── README.md               # 모듈 표와 변수 표. 아래 "프로젝트 README" 형식
│   ├── {도메인}.sql
│   └── {도메인}.sql
└── {이슈번호}/
    └── seeds.sql               # 이 이슈의 변수 블록만
```

## seeds.sql: 변수 블록만

`.claude/resources/perf/{이슈번호}/seeds.sql`에는 **변수 블록만** 쓴다. 모듈 본문을 복사하지 마라.

```sql
-- PERF-{이슈번호} 시드
-- 대상: {측정할 엔드포인트들}
-- 규모 근거: 운영 대비 {배수}. {무엇을 관측하려는지}

{세션 설정. 예: MySQL 재귀 CTE 깊이 상한}

-- {도메인 1}
{변수} = {값};   -- {뜻. k6의 ID_START / USER_COUNT, mint-tokens.sh의 --start / --count와 맞출 값이면 그렇다고 적는다}

-- {도메인 2}
{변수} = {값};
```

## 실행: cat으로 이어 붙인다

호출자가 레포 루트에서 실행한다. 변수 블록과 모듈을 호스트에서 이어 붙여 표준입력으로 넘긴다.
DB 클라이언트가 컨테이너 안에서 돌면 `SOURCE`나 `\i`는 호스트 경로를 못 본다. `cat`은 어느 쪽에서도 같다.

```bash
cat "$PERF_DIR/seeds.sql" "$SEEDS/{모듈 1}.sql" "$SEEDS/{모듈 2}.sql" | dbq
```

`cat` 순서가 곧 FK 의존 순서다. 필요 없는 모듈은 뺀다.

## 모듈 본문

모듈 하나는 아래 순서를 따른다.

```sql
-- {도메인} 시드: {채우는 테이블}
--
-- 필요한 변수: {변수 목록}
-- 선행 모듈: {없음 / 모듈}
-- {id 범위, 다른 모듈이나 k6와 맞물리는 값의 설명}

{적재: 변수로 행 수와 카디널리티를 정하는 INSERT ... SELECT}

{통계 갱신: 이 모듈이 채운 테이블}

-- 검증
SELECT '{테이블}'                  AS table_name,
       count(*)                    AS rows_seeded,
       count(DISTINCT {컬럼})      AS {컬럼}_cardinality,
       min(id)                     AS min_id,
       max(id)                     AS max_id
FROM {테이블}
WHERE id BETWEEN {시작 변수} AND {시작 변수} + {개수 변수} - 1;
```

규칙:

- **검증 쿼리는 모듈 말미에 둔다.** 행 수와 함께 카디널리티를 반드시 뽑는다. Phase 3-A가 이 값을 확정값과 대조한다.
- id는 명시 삽입하고 시작값을 변수로 둔다. 앱 시드와 겹치지 않게 충분히 큰 값을 쓴다. 겹치면 시드 정리가 실제 데이터를 지운다.
- 재실행해도 중복이 쌓이지 않아야 한다. 중복 가드(UNIQUE 제약과 무시 삽입)를 지우지 마라.
- 카디널리티가 걸린 컬럼은 `n % 변수`로 서로 다른 값의 개수를 명시적으로 통제한다. 한 값에 전 행이 몰리거나 전 행이 서로 다른 값을 갖게 두지 마라.
  분포의 치우침이 필요하면 그 규칙을 주석으로 남긴다.
- enum 성격의 컬럼에는 **애플리케이션 코드에 실재하는 상수명만** 넣는다. 앱이 이름으로 파싱하면 없는 값은 조회 시점에 500이다. DB는 문자열이라 들어갈 때는 통과한다.
- 값이 실제 데이터처럼 보일 필요는 없다. FK, 개수, 카디널리티만 맞으면 된다 (`'perf-item-' || n` 수준).
- 쓰기 엔드포인트를 잴 때 부하가 쓰려는 행을 미리 채워두면 전부 중복 실패다. 그 행을 만드는 변수를 0으로 둘 수 있게 만든다.
- 특정 이슈의 숫자를 본문에 박지 마라. 새 도메인은 기존 모듈에 덧붙이지 말고 새 모듈 파일로 만든다.

## 모듈을 만들거나 고칠 때

- **실제 스키마와 먼저 대조하라.** 마이그레이션이 추가돼도 모듈은 따라오지 않는다. stacks 파일 **시드** 절의 필수 컬럼 조회로
  NOT NULL, 기본값 없는 컬럼을 뽑아 INSERT 컬럼 목록과 맞춘다.
- enum 값은 엔티티의 enum 파일을 기준으로 한다.
- 고친 모듈은 커밋 전에 한 번 실행하고 검증 결과를 확인한다.
- 프로젝트 README의 모듈 표와 변수 표를 함께 고친다.

## 대량 적재

모듈의 행 생성 방식(재귀 CTE, `generate_series`)은 **수십만 행까지**가 편한 범위다. 그 이상이면 아래를 함께 한다.

1. 목표 규모가 DB 버퍼보다 크면 측정이 디스크 I/O를 잰다. 그 사실을 Phase 3에서 먼저 확정한다.
2. 적재를 느리게 하는 보조 구조(전문 검색 인덱스 등)는 떼고 넣고 다시 만든다. 떼어 둔 동안 그 구조를 쓰는 API를 호출하지 마라.
3. 적재 세션에서만 무결성 검사를 끈다. 전역 내구성 설정은 건드리지 마라. 되돌리지 않으면 측정이 운영과 다른 조건에서 돈다.
4. 모듈 단위로 한 트랜잭션에 묶고, 끝나면 통계를 갱신한다.
5. 적재 뒤 Phase 2의 스키마 드리프트 점검을 다시 돌린다. 대량 적재 전후로 인덱스가 사라진 사례가 있다.

DB별 구체 명령은 stacks 파일 **시드** 절.

## 시드를 지울 때

id를 명시 삽입했으므로 범위로 지운다. FK가 `ON DELETE CASCADE`면 부모 테이블만 지워도 나머지가 따라 지워진다. 아니면 자식부터 지운다.

```sql
DELETE FROM {자식 테이블} WHERE {부모 id 컬럼} BETWEEN {시작} AND {끝};
DELETE FROM {부모 테이블} WHERE id BETWEEN {시작} AND {끝};
```

## 프로젝트 README 형식

`perf.seedsDir/README.md`는 아래 두 표를 가진다. 모듈을 추가하면 두 표에 행을 추가한다.

| 모듈 | 채우는 테이블 | 선행 모듈 |
|---|---|---|
| `{도메인}.sql` | `{테이블}` | 없음 |

| 변수 | 모듈 | 뜻 | 상한 |
|---|---|---|---|
| `{변수}` | {모듈} | {뜻. k6, mint-tokens.sh와 맞출 값이면 명시} | {목록 길이 등 상한이 있으면} |

> 예시 (MySQL 수강신청 프로젝트): `member.sql`(회원), `course.sql`(강의와 시간표), `enrollment.sql`(장바구니, 수강신청과 현재 인원 동기화)
> 세 모듈을 두고, 학과 수와 영역 수를 `ELT` 목록 길이 안에서 변수로 정했다. 담기 상한이 10인 도메인 규칙을 변수 상한 칸에 적어
> 상한을 넘긴 시드로 쓰기 API가 항상 실패하는 측정을 막았다.
