── 작성 규칙 (이 블록은 산출물에 남기지 마라) ──────────────
이 파일은 `harness perf-query-stats`가 만드는 가공본의 형태와, 스킬이 채우는 칸의 규칙이다. 가공본을 손으로 처음부터 쓰지 마라.

변환기가 하는 일 (손대지 마라)
- 수치 계산과 자릿수: 요청당, 행/호출, 읽은행/반환행, 블록/호출은 소수 4자리, mean_ms와 total_ms는 6자리, 비중은 4자리 %.
  0이 아닌 값이 반올림으로 0이 되면 유효숫자 2개가 나올 때까지 자릿수를 늘린다. MySQL의 피코초는 ms로 바꿔 둔다.
- 행 순서: total_ms 내림차순. 재정렬하지 마라. 상위 `perf.queryStatsTop`건 밖은 합계 한 줄로 접는다.
- 트랜잭션 제어문(`COMMIT`, `ROLLBACK`, `BEGIN`, `SET autocommit` 등)은 출처 `-`, 하는 일 `트랜잭션 제어`로 채운다.
  빼지 않는다. 요청당 트랜잭션 수의 근거다.
- 쿼리 원문: 1차 출력 전문 그대로. 리터럴은 `?`나 `$1`로 치환된 상태로 둔다. 원문이 `...`로 끝나면 잘렸다는 한 줄을 붙인다.
- `{n}` ≥ 1이면 직전 가공본(`-{n-1}`)과 같은 원문의 쿼리를 대조해 **직전 상태 대비** 줄과 표를 쓰고, 같은 원문의 출처와 하는 일을 옮긴다.
  원문이 한 글자라도 바뀐 쿼리는 사라짐과 새로 생김으로 나온다.

스킬이 하는 일 (`{출처}`, `{하는 일}` 칸만)
1. **출처**는 확인된 것만 적는다. `{클래스}.{메서드}` 형태로 쓰고, 확인하지 못했으면 `미상`으로 둔다. 그럴듯한 이름을 지어내지 마라.
   Phase 1에서 확정한 예상 쿼리 목록과 `jvm-metrics-{n}.md`의 리포지토리 호출 표가 1차 후보다.
   목록에 없으면 인증 필터, 인터셉터, 이벤트 리스너, ORM 내부 조회를 의심한다.
2. **하는 일**에는 그 쿼리가 무엇을 읽고 쓰는지만 한 줄로 적는다.
   왜 느린지, 문제인지, 고쳐야 하는지는 쓰지 마라. 이 파일에는 사실만 남는다.
3. 원문이 바뀌어 새로 생김으로 나온 쿼리가 직전의 어느 쿼리와 같은 출처인지는 하는 일 칸 끝에 `(직전 [k]의 원문 변경)`으로 적는다.
4. 그 외 줄과 칸은 고치지 마라. 수치를 다시 쓰거나 반올림하지 마라.
