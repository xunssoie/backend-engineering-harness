## Phase 5. 기법 선택과 설계

### 목적
Phase 4의 재현 결과에 근거해 동시성 제어 기법 후보를 제시하고, 이번 후보의 설계를 호출자와 확정한다.

**게이트.** 기법과 설계를 스킬이 단독으로 확정하지 마라.

### 선행 조건
- Phase 4 완료 (위반이 재현되어 있다)
- 코드가 원본 상태다. 앞 후보를 적용했다면 Phase 7에서 되돌린 뒤 여기로 온다

### 참조 파일
- 주입된 `stack`의 **제약과 인덱스**, **동시성 측정에서만 걸리는 것** 절
- `.claude/spec/service-policy/` (대상 도메인 파일이 있으면)

### 절차

#### 5-A. 후보 제시

1. 재현 결과에 근거해 기법을 표로 제시한다.

   | # | 기법 | 경합을 어디서 막는가 | 기대 | 비용, 리스크 |
   |---|---|---|---|---|

   - **근거에는 Phase 4에서 관측된 수치를 쓴다.** 일반론으로 채우지 마라.
   - 이 표에는 기법 이름과 성격까지만 적는다. 구체 설계는 5-B에서 확정한다.
   - 아래 카탈로그에서 이번 대상에 성립하는 것만 골라 제시한다. 전부 나열하지 마라.

   | 기법 | 막는 지점 | 특징 |
   |---|---|---|
   | 원자적 조건부 UPDATE | DB 한 문장 안 | 읽기와 쓰기가 한 문장이라 인터리빙이 끼어들 틈이 없다. 영향 행 수로 실패를 판정한다 |
   | 비관적 락 (`SELECT ... FOR UPDATE`) | 트랜잭션 구간 | 임계 구역을 직렬화한다. 정확하지만 핫 로우에서 전 요청이 줄을 선다 |
   | 낙관적 락 (버전 칼럼) + 재시도 | 커밋 시점 | 충돌한 쪽만 실패하고 재시도한다. 충돌이 잦으면 재시도가 폭증한다 |
   | DB 제약 (`CHECK`) | 저장 시점 | 최후 방어선. 단독으로는 쓸 수 없고 사용자에게 돌려줄 응답이 없다 |
   | 분산 락 (Redis, MySQL `GET_LOCK`, PostgreSQL 권고 락) | 애플리케이션 밖 | 인스턴스가 여럿일 때 의미가 생긴다. 락 해제 실패와 만료 설계가 따라온다 |
   | 원자 카운터 (Redis `DECR`) + 비동기 영속화 | 인메모리 | 처리량이 가장 높다. DB와의 정합성 복구 설계가 반드시 필요하다 |

   - Phase 4가 이미 답을 준 기법은 그 근거를 대고 제외를 권한다.
     (예: 락 대기가 요청 수만큼 일어났는데도 갱신이 유실됐다면 문제는 직렬화 부족이 아니라 락 밖에서 읽은 낡은 값이다)
   - 다른 경로가 같은 칼럼을 벌크 UPDATE로 고치면 버전 칼럼이 올라가지 않아 낙관적 락이 충돌을 못 잡는다. 반대편 경로까지 확인한다.

2. **한 후보에 한 기법만 올린다.** 표를 보고하고 호출자의 선택을 기다린다.
   - 이미 잰 후보가 있으면 `harness conc-compare {대상 디렉토리}`의 표를 함께 보여준다. 남은 후보 중에서 고르게 한다.
   - 순서를 스킬이 임의로 정하지 마라. 다만 호출자가 순서를 물으면
     **단순한 것부터** 권한다. 원자적 UPDATE와 비관적 락이 설계 변수가 가장 적다.

#### 5-B. 설계 협의

호출자가 설계하고 스킬이 검증한다. `SKILL.md`의 **분석 주도 규칙**을 따르되, 여기서는 해석이 아니라 설계가 대상이다.

3. 판단 재료를 먼저 전부 펼친다.
   - 임계 구역 코드와 현재 발행되는 SQL (Phase 1의 기록)
   - 대상 테이블의 제약과 인덱스. `stack`의 **제약과 인덱스** 절의 명령을 제시한다
   - 재현 결과의 위반 양상 (상한 초과인지, 카운터 유실인지, 둘 다인지)

4. 결정할 항목을 나열하고 **한 번에 하나씩** 묻는다.

   | 기법 | 호출자가 결정할 항목 |
   |---|---|
   | 원자적 조건부 UPDATE | 조건절에 넣을 불변식, 영향 행 수가 0일 때 던질 예외와 응답 코드, 갱신을 저장소 계층으로 내릴지 |
   | 비관적 락 | 락 범위(대상 행만인지 조회 전체인지), 락 획득 순서, 대기 타임아웃, 타임아웃 시 응답 |
   | 낙관적 락 | 재시도 횟수 상한, 재시도 간격, 상한 초과 시 응답, 버전 칼럼 마이그레이션 |
   | DB 제약 | 제약 위반 예외를 어느 응답 코드로 옮길지 |
   | 분산 락 | 락 키 구성, 만료 시간, 해제 실패 처리, 인프라 추가 여부 |
   | 원자 카운터 | 영속화 시점, 장애 시 복구 절차, 허용할 정합성 지연 |

   - 정답을 먼저 말하지 마라. 결정에 필요한 사실만 주고 답을 기다린다.
   - 질문을 몰아서 하지 마라.
   - 영향 행 수가 0이 되는 원인이 여럿이면(무결성이 이미 깨짐, 동시 중복 요청) 원인별로 그 결정의 효과를 표로 보여준다.

5. 호출자의 답마다 판정한다. **동시성 설계에서 자주 놓치는 것**을 반드시 짚는다.

   - **트랜잭션 경계 밖의 락은 락이 아니다.** 트랜잭션이 없는 메서드에 `FOR UPDATE`를 걸면
     조회 직후 락이 풀린다
   - **락을 잡기 전에 읽은 값은 이미 낡았다.** 락 획득 후 다시 읽어야 한다
   - **버전 칼럼은 같은 트랜잭션이 그 엔티티를 실제로 변경할 때만 올라간다.** 읽기만 하면 충돌을 못 잡는다
   - **여러 행에 락을 잡을 때 순서가 다르면 데드락이다.** 항상 같은 기준으로 정렬해 잡는다
   - **재시도는 트랜잭션 밖에서 해야 한다.** 롤백된 트랜잭션 안에서 재시도하면 그대로 다시 롤백된다
   - **격리 수준에 따라 일반 `SELECT`가 읽는 값이 다르다.** MySQL `REPEATABLE READ`는 트랜잭션 스냅샷을,
     PostgreSQL `READ COMMITTED`는 문장 시점 값을 읽는다. 갱신 직전 확인이 필요하면 잠금 읽기로 현재 값을 읽어야 한다
   - **조건부 UPDATE의 영향 행 수를 확인하지 않으면 아무것도 막지 못한다.** 반환값을 반드시 판정에 쓴다
   - **역방향 동작에도 같은 제어를 걸어야 한다.** 증가만 막고 감소를 두면 카운터가 다시 어긋난다
   - **조건 없는 원자적 UPDATE는 유실만 막는다.** 상한, 하한 불변식은 조건절이 지킨다

   - 서비스 정책이 걸린 설계면 `.claude/spec/service-policy/`의 해당 도메인 파일을 읽고 어긋나는지 확인한다.

6. 호출자의 설계가 최선이 아니어도, 동작하고 위험하지 않으면 그대로 진행한다.
   - 더 나은 대안이 있으면 근거와 함께 제시한다. 호출자가 자기 안을 고수하면 그대로 진행한다.
   - **불변식을 지키지 못하는 설계일 때만** 진행을 중단하고 근거를 설명한다.
     이 스킬의 목적이 불변식을 지키는 것이므로, 그것을 못 지키는 설계는 후보가 될 수 없다.

7. 확정된 설계와 **예상 결과**를 `record.md`의 후보 {n} **설계 결정**에 기록한다.
   예상은 정합성과 경합 두 축으로 각각 받는다.
   - 정합성: 어느 불변식이 어떻게 지켜지는가
   - 경합: 처리량이 어느 방향으로 얼마나 움직일 것 같은가
   - 예상의 전제가 이 후보에 그대로 성립하지 않을 수 있으면(예: 락을 새로 걸지 않는 기법인데 "처리량이 떨어진다"고 예상) 단서를 덧붙인다.
     판정은 Phase 7의 실측이 한다.

8. 진행 상태에 이번 후보 행을 추가하고 기법을 적는다. 행이 없으면 CLI가 덧붙인다.

   ```bash
   harness conc-progress {record.md 경로} --phase 5 --mark ✅ --candidate {n} --technique "{기법}"
   ```

### 출력
- `record.md`에 후보 {n} 섹션이 생성되고, 기법과 **설계 결정**이 확정됨
- 진행 상태의 후보 {n} Phase 5가 ✅

### 실패 처리
- 호출자가 고른 기법이 이번 대상에서 성립하지 않으면(예: 단일 인스턴스인데 분산 락)
  그 근거를 대고 다른 후보를 권한다.
