## Phase 2. 측정 환경 검증

### 목적
측정값을 왜곡하는 설정이 없는지, 쿼리 단위 관측 도구와 캐시 제어 수단이 유효한지, 로컬 스키마가 마이그레이션과 같은지 확인한다.

**게이트.** 하나라도 통과하지 못하면 넘어가지 마라. 호출자에게 조치를 요청한다.

### 선행 조건
- Phase 1 완료

### 참조 파일
- `perf.profileConfigFile` (측정 프로파일 정의)
- `stackGuide` (주입된 맥락의 stacks 파일)
- `.claude/skills/optimize-performance/template/perf-env.sh`

### 절차

1. `perfConfigured`가 false면 먼저 `.claude/harness.json`의 `perf` 절을 호출자와 채운다.
   최소 `db`, `dbName`, `dbUser`, 비밀번호 출처(`dbPasswordEnv` 또는 `dbPassword`), `dbContainer` 또는 `dbHost`/`dbPort`, `appBaseUrl`, `managementUrl`, `tokens`.
   값은 프로젝트의 compose 파일, 프로파일 설정, README에서 찾아 제안하고 확답을 받는다. 지어내지 마라.
   harness.json 수정은 훅이 확인을 묻는다.

2. `perf.profileConfigFile`을 Read해 커넥션 풀 크기, SQL 로깅, 드라이버, 캐시 접속을 확인한다.
   이 파일이 측정 프로파일의 유일한 정의다. SQL 로깅이나 p6spy가 켜져 있으면 끄도록 요청한다.
   요청당 수십 줄을 찍는 로깅은 측정값을 통째로 바꾼다.

3. 셸 환경과 서버 기동을 제시한다. 애플리케이션은 별도 터미널에서 띄우게 하고, 기동 완료를 확인받은 뒤 4로 간다.

   ```bash
   # 측정 터미널 (레포 루트)
   source .claude/skills/optimize-performance/template/perf-env.sh {이슈번호} {슬러그}
   docker compose -f {perf.composeFile} up -d {DB 서비스} {캐시 서비스}   # compose를 쓰는 프로젝트만

   # 애플리케이션 터미널
   {perf.appStartCommand}
   ```

4. 아래를 **순서대로** 실행하게 하고 결과를 받는다. 3)은 2)가 만든 미터를 세므로 2)를 건너뛰지 마라.

   ```bash
   # 0) DB 접속과 charset. stacks 파일 **접속 점검** 절의 쿼리를 쓴다 (한글 등 비ASCII 컬럼 하나를 읽는다)

   # 1) 측정 프로파일로 떠 있는가 (application 태그에 프로파일이 드러나게 설정했다면 그 값)
   curl -s "$PERF_METRICS_URL" | grep -m1 'application='

   # 2) 미터 등록용 1회 요청. 메인 포트(PERF_APP_URL)여야 한다. 관리 포트 요청은 메인 서버 미터를 만들지 않는다. 401이어도 기록된다
   curl -s -o /dev/null -w '%{http_code}\n' "$PERF_APP_URL{대상 경로}"

   # 3) 응답시간 히스토그램 (0이면 SLO 버킷 설정이 안 붙은 것)
   curl -s "$PERF_METRICS_URL" | grep -c http_server_requests_seconds_bucket

   # 4~7) 쿼리 통계 활성화, 통계가 채워지는지, 원문 잘림, 버퍼 크기. stacks 파일 **Phase 2 점검** 절의 블록을 그대로 쓴다

   # 8) 애플리케이션 캐시 (perf.cachePingCommand가 있을 때만). 응답이 없으면 캐시 오류 처리기가 DB로 폴백해 캐시 없는 상태를 재게 된다
   {perf.cachePingCommand}

   # 9) JVM 샘플러가 긁을 지표가 다 있는가 (게이트 7개 모두 "있음")
   bash "$PERF_SCRIPTS/jvm-sampler.sh" check

   # 10) 마이그레이션이 선언한 인덱스가 실제 DB에 있는가. stacks 파일 **스키마 드리프트** 절. 아무것도 출력되지 않아야 한다
   ```

5. 실패 항목의 조치:
   - 3)이 0 → 설정을 의심하기 전에 2)를 메인 포트로 보냈는지 확인한다.
   - 8) 실패 → 캐시 컨테이너 기동 상태를 확인한다.
   - 9)에서 `pool`, `http_active` 없음 → 2)를 메인 포트로 보냈는지 확인한다. `gc` 없음 → 아직 GC가 없던 것이니 2)를 몇 번 더 보내고 재시도한다.
     풀이 HikariCP가 아니거나 지표 이름이 다르면 `perf.metrics`를 고친다. 그 외가 없음 → 1)로 돌아가 측정 프로파일로 떴는지 확인한다.
   - 0), 4~7) 실패 → stacks 파일 **Phase 2 점검** 절의 조치를 따른다.
   - 10)이 하나라도 출력 → **로컬 DB가 마이그레이션이 선언한 스키마와 다르다.** 그대로 재면 없는 병목을 최적화하게 된다.
     출력된 이름을 그대로 보이고 stacks 파일 **스키마 드리프트** 절의 확인과 복구를 따른다.
     복구는 해당 마이그레이션의 인덱스 생성문을 **그대로** 실행한다. 정의를 새로 쓰지 마라. 복구 뒤 통계를 갱신하고 10)을 다시 돌린다.
     무엇이 지웠는지 특정하지 못해도 복구하고 진행하되 그 사실을 적는다. 추측을 원인으로 단정해 적지 마라.
   - 10)의 통과 기준: 원칙은 출력이 빌 때까지 복구하는 것이다. 다만 남은 누락이 **이번 대상의 쿼리가 읽지 않는 테이블**의 것뿐이면
     통과로 처리해도 된다. 그때는 남은 이름과 그 근거를 `record.md`의 **스키마 드리프트**에 반드시 적는다.
     이 검사는 선언됐는데 없는 인덱스만 찾는 단방향 대조다. 추가 인덱스나 정의가 다른 인덱스는 걸러내지 못하고, 운영 DB 상태도 알려주지 않는다.
   - 실행계획에 예상 밖의 풀스캔이 나왔을 때 "옵티마이저가 인덱스를 고르지 않았다"고 해석하기 전에 10)을 먼저 확인한다.

6. 결과를 `record.md`의 **측정 환경**에 적는다. 프로파일, 커넥션 풀 크기, DB 버퍼 크기, 캐시 상태와 제어 수단, 스키마 드리프트.
   캐시 상태 기본은 warm 고정이다. DB 버퍼는 보통 재기동 없이 비울 수 없으므로 Phase 4와 8이 같은 워밍업으로 상태를 맞춘다.
   애플리케이션 캐시를 비운 상태(cold)를 재려면 Phase 3-B에서 확정하고, 그 방법(`perf.cacheFlushCommand`)을 적는다.
   애플리케이션 캐시를 비워도 DB 버퍼는 그대로다. 둘을 묶어 cold라고 적지 마라.

### 출력
- `record.md`의 **측정 환경**에 프로파일, 풀 크기, 버퍼 크기, 캐시 상태, 스키마 드리프트
- `harness perf-progress {record.md} --phase 2 --mark ✅`

> 다음 Phase 조건: 4의 항목이 모두 통과했을 때 → Phase 3
>
> Skip 조건: 같은 이슈의 다른 대상에서 통과했고 그 사이에 애플리케이션과 컨테이너를 재기동하지 않았으면,
> 앞선 대상의 **측정 환경**을 옮겨 적고 ⏭️로 표기한다. 단 그 사이에 아래 중 하나라도 있었으면 10)은 다시 확인한다.
> 앱을 재기동하지 않아도 DB는 바뀐다. 무엇이 있었는지 확신할 수 없으면 다시 확인한다.
>
> - Phase 3-A의 시드 실행 (대량 적재 전후에 인덱스가 사라진 사례가 있다)
> - 인덱스 복구, 추가, 삭제, 마이그레이션 실행
> - 앞선 대상이 통과 기준의 예외(대상 밖 테이블)로 넘어갔고, 이번 대상이 그 테이블을 읽는 경우
