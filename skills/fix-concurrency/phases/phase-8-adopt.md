## Phase 8. 채택과 보고

### 목적
후보들을 한 표에 놓고 하나를 채택한다. 채택안을 코드에 되살리고 최종 검증한 뒤 보고한다.

**채택 근거가 남아야 개선이 완결된다.** 무엇을 골랐는지보다 왜 그것을 골랐는지가 기록의 값어치다.

### 선행 조건
- 후보가 하나 이상 Phase 7까지 끝났다
- 코드가 원본 상태다 (모든 후보가 stash로 보관되어 있다)

### 참조 파일
- `.claude/skills/fix-concurrency/template/output.md`

### 절차

1. **후보 비교표를 구성해 제시한다.**

   ```bash
   harness conc-compare {대상 디렉토리}
   ```

   - 출력 표를 그대로 쓴다. 받지 못한 값을 추정해 채우지 마라. 빈 칸(`-`)은 `missing`의 파일이 없어서다.
   - **정합성을 확보하지 못한 후보는 표에 남기되 채택 후보에서 빼고, 뺀 이유를 적는다.**
     지운 후보는 기록에서 사라지면 안 된다. 무엇이 안 통했는지가 근거다.
   - 처리량 차이를 절대값으로 단정하지 마라. 로컬 측정이므로 **후보 간 상대 비교**로만 쓴다.
   - 재지 않고 제외한 기법도 배제 이유와 함께 남긴다(Phase 5-A에서 제외, 재지 않음).

2. **채택을 호출자에게 묻는다.** `SKILL.md`의 **분석 주도 규칙**을 따른다.
   - 물을 것: "이 표에서 어떤 후보를 채택하시겠습니까? 무엇을 근거로 삼으시겠습니까?"
   - 스킬이 먼저 답을 말하지 마라. 호출자가 막히면 그때 판단 축을 제시한다.

     | 축 | 무엇을 보는가 |
     |---|---|
     | 정합성 | 모든 후보가 위반 0이면 이 축은 변별력이 없다 |
     | 처리량 대가 | 정합성이 같다면 대가가 작은 쪽 |
     | 실패 응답의 품질 | 거절이 의도한 코드로 나가는가, 500이 섞이는가 |
     | 운영 비용 | 스키마 변경, 인프라 추가, 복구 절차의 유무 |
     | 코드 위치 | 도메인에 남는가, SQL로 내려가는가 |

   - 호출자가 처리량이 가장 좋은 후보를 골랐는데 그 후보에 운영 비용이 크면 그 사실을 짚는다.
     짚기만 하고, 고수하면 그대로 진행한다.

3. **채택안을 코드에 되살린다.**

   ```bash
   git stash list
   git stash apply {채택한 후보의 stash}
   git status --short
   ```

   - 후보 전용 스키마가 있었으면 마이그레이션 파일도 함께 되살아났는지 확인한다.
   - 채택하지 않은 후보의 stash는 남겨둔다. 지우지 마라. 기록의 일부다.
     정리가 필요하면 호출자에게 확인받는다.
   - Phase 6에서 미뤄둔 측정과 무관한 정리(죽은 코드 제거 등)는 여기서 한다.

4. **되살린 코드로 최종 검증을 한 번 더 돌린다.** stash 적용 과정에서 어긋났을 수 있다.

   - 테스트를 `harness run-tests`로 실행한다.
   - 애플리케이션을 재기동(`restart-app.sh`)한 뒤 `n=final`로 측정하도록 제시한다.

     ```bash
     bash .claude/skills/fix-concurrency/template/measure.sh {이슈번호} {슬러그} final
     ```

     ```bash
     harness conc-burst-summary {대상 디렉토리}/k6-burst-raw-final.json \
       --base {대상 디렉토리}/k6-burst-summary-0.json \
       --out {대상 디렉토리}/k6-burst-summary-final.json
     harness conc-compare {대상 디렉토리}
     ```

   - `final` 행의 위반이 0이 아니면 stash 적용이 온전하지 않은 것이다. 원인을 짚고 보고한다.

5. **운영 반영 시 유의점을 정리한다.**

   | 확인 | 내용 |
   |---|---|
   | 마이그레이션 | 추가한 파일과 운영 데이터에 미치는 영향. 없으면 "스키마 변경 없음" |
   | 인프라 | 추가로 필요한 것(Redis 등). 없으면 "추가 없음" |
   | 기존 데이터 | 이미 어긋난 집계가 운영에 있으면 보정 SQL이 필요한지 |
   | 인스턴스 수 | 채택한 기법이 다중 인스턴스에서도 성립하는지 |

   - 마지막 항목을 빠뜨리지 마라. 단일 인스턴스에서만 성립하는 제어(애플리케이션 레벨 락 등)를
     채택했으면 그 제약을 명시한다.
   - 새로 만든 실패 응답이 로그에 원인을 남기는지도 본다. 예외 메시지가 비어 로그에 `null`만 찍히면 손상이 드러나지 않는다.

6. `record.md`의 **최종 요약**을 채운다. 후보 비교표, 채택 결정과 근거, 운영 반영 시 유의점을 적는다.
   진행 상태를 갱신한다.

   ```bash
   harness conc-progress {record.md 경로} --phase 8 --mark ✅
   ```

7. 보고 템플릿을 Read로 읽어 그 규격대로 보고한다.
   - `.claude/skills/fix-concurrency/template/output.md`

8. 같은 이슈에 다른 임계 구역이 남아 있으면 그 사실을 알린다. 새 슬러그 디렉토리로 Phase 1부터 시작한다.

### 출력
- 채택한 후보의 코드가 작업 트리에 반영됨
- `invariant-final.txt`, `k6-burst-summary-final.json`, `lock-stats-final.txt` 생성
- `record.md`의 **최종 요약**에 비교표, 채택 근거, 운영 반영 시 유의점이 기록
- 진행 상태의 Phase 8이 ✅

### 실패 처리
- 정합성을 확보한 후보가 하나도 없으면 채택하지 않는다. 그 사실을 그대로 보고하고
  Phase 5로 돌아가 다른 기법을 후보로 올릴지 호출자에게 묻는다. **억지로 하나를 고르지 마라.**
- `git stash apply`가 충돌하면 충돌 파일을 보고하고 호출자의 판단을 받는다.
