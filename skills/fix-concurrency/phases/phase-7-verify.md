## Phase 7. 검증과 되돌리기

### 목적
Phase 4와 **완전히 동일한 조건**으로 재측정해 이 후보가 불변식을 지키는지 확정하고,
정합성을 얻은 대가를 경합 지표로 잰다. 마지막에 코드와 데이터를 되돌려 다음 후보를 받을 상태로 만든다.

### 선행 조건
- Phase 6 완료
- 애플리케이션이 후보 {n}의 코드로 재기동되어 있다

### 절차

1. **Phase 4와 같은 명령을 `n`만 바꿔 실행하도록 제시한다.**
   VU, 허용 상한, 시드 규모, 커넥션 풀 크기를 하나도 바꾸지 마라.

   ```bash
   bash .claude/skills/fix-concurrency/template/measure.sh {이슈번호} {슬러그} {n}
   ```

   - **되돌리기를 절대 건너뛰지 마라.** `measure.sh`가 `reset.sql`을 먼저 돌리고 `reset_ok`가 1이 아니면 멈춘다.
     Phase 4가 남긴 행이 그대로 있으면 상한이 이미 찬 상태에서 재게 되어 전 요청이 실패한다.
     그 결과는 "정합성이 지켜졌다"로 보이지만 아무것도 검증하지 못한 것이다.
   - 조건이 달라졌으면 그 사실을 기록에 명시하고, 비교 가능한 범위를 좁혀서 해석한다.

2. 실행이 끝나면 원본을 가공한다. 터미널 출력을 붙여넣게 하지 마라.

   ```bash
   harness conc-burst-summary {대상 디렉토리}/k6-burst-raw-{n}.json \
     --base {대상 디렉토리}/k6-burst-summary-0.json \
     --out {대상 디렉토리}/k6-burst-summary-{n}.json
   harness conc-compare {대상 디렉토리} --candidate {n}
   ```

   - `conc-burst-summary`가 `k6-burst-summary-{n}.json` 최상위에 `delta_vs_base`를 붙인다. 손으로 덧붙이지 마라.
   - `conc-compare --candidate`가 정합성 표와 경합 표를 `-0` 대비로 만든다.
     **비교 대상은 항상 `-0`이다.** 앞 후보(`-{n-1}`)와 비교하지 마라. 후보는 누적되지 않는다.
   - `warnings`(조건 불일치)가 있으면 해석 전에 호출자에게 알린다.

3. **정합성부터 판정한다. 이것이 1급이고, 여기서 실패하면 경합 지표는 볼 필요가 없다.**

   `conc-compare`의 정합성 표를 그대로 제시한다.

   | 조건 | 판정 |
   |---|---|
   | 모든 불변식의 위반이 0 | **정합성 확보** |
   | 하나라도 0이 아님 | **실패.** 설계가 경합을 못 막았다 |

   - 실패했으면 **수치를 유리하게 해석하지 마라.** "위반이 줄었다"는 성공이 아니다.
     불변식은 참 아니면 거짓이다.
   - 실패 원인을 짚어 보고하고 호출자의 판단을 받는다. 설계를 고쳐 같은 후보를 다시 잴지,
     이 기법을 배제하고 다음 후보로 갈지는 호출자가 정한다.
   - 참고 지표(전체 자원의 집계 어긋남 등)도 `invariant-{n}.txt`에서 Read해 함께 본다.

4. 정합성을 확보했으면 **대가를 잰다.** 이것이 채택 근거가 된다.

   `conc-compare`의 경합 표를 그대로 제시한다. 재시도 횟수(낙관적 락만)는 애플리케이션 카운터로 받아 덧붙인다.

   - **처리량이 떨어졌다는 이유로 실패 판정을 내리지 마라.** 동시성 제어는 거의 항상 처리량을 깎는다.
     이 표는 실패 판정용이 아니라 후보 간 비교용이다.
   - 응답 코드 분포를 함께 본다. 상한 초과로 거절된 요청이 **의도한 코드**로 나가는지 확인한다.
     500이 섞여 있으면 정합성은 지켰어도 사용자 경험은 깨진 것이다. 그 사실을 명시한다.
   - 데드락 증가분이 0이 아니면 `lock-stats-{n}.txt`의 `LATEST DEADLOCK` 구간을 Read해 원문을 함께 제시한다.
   - 락 대기 수가 같은데 대기 시간이 줄었다면 락을 쥔 채로 하던 일의 양이 줄어든 것이다. 그 경우 락 **이전**의 변화(조회 제거 등)와
     락 **안**의 변화(UPDATE 문장 자체)를 구분해 짚는다.

5. Phase 5-B에 적힌 **예상 결과**와 실측을 대조해 보고한다.
   - 예상대로면 어떤 근거가 맞았는지 짚는다.
   - 어긋났으면 어느 가정이 틀렸는지 관측값으로 짚는다.
   - 실측 없이 "예상대로 되었다"고 쓰지 마라.

6. 결과를 `record.md`의 후보 {n} **검증 결과**에 채운다.

7. **코드와 데이터를 되돌린다.** 이 단계를 빼먹으면 다음 후보의 측정이 오염된다.

   ```bash
   # 코드
   git stash push -u -m "candidate-{n}-{기법}" -- . ':(exclude).claude/resources/concurrency'
   git status --short          # 측정 산출물 외에는 비어 있어야 한다

   # 후보 전용 스키마를 추가했으면 Phase 6의 되돌리기 SQL을 실행한다

   # 데이터
   eval "$(.claude/scripts/harness conc-shell --issue {이슈번호} --slug {슬러그})"
   dbc < "$TARGET_DIR/reset.sql"
   ```

   - 측정 산출물(`.claude/resources/concurrency/`)은 stash에 넣지 마라. 기록이 함께 사라진다.
   - `git stash`로 보관하면 Phase 8에서 채택된 후보를 `git stash apply`로 되살릴 수 있다.
     stash 메시지에 후보 번호와 기법을 남긴다.
   - stash 목록을 `record.md`의 후보 {n} **되돌리기**에 적는다.

     ```bash
     git stash list
     ```

   - 애플리케이션을 원본 코드로 재기동한다(`restart-app.sh`).
   - 진행 상태를 갱신한다.

     ```bash
     harness conc-progress {record.md 경로} --phase 7 --mark ✅ --candidate {n}
     ```

8. 다음 후보를 잴지 호출자에게 확인한다.

   | 조건 | 다음 |
   |---|---|
   | 재고 싶은 후보가 남았고 호출자가 계속을 선택 | Phase 5 (후보 번호 +1) |
   | 호출자가 비교를 끝내기로 선택 | Phase 8 |

   **판정만 하고, 계속할지는 호출자에게 확인한다.**
   - 후보가 하나뿐이고 바로 채택하기로 했으면 7번의 stash 왕복을 생략할 수 있다. 그 편차와 이유를 **되돌리기**에 남긴다.

### 출력
- `invariant-{n}.txt`, `k6-burst-raw-{n}.json`, `lock-stats-{n}.txt` (호출자), `k6-burst-summary-{n}.json`(`delta_vs_base` 포함, 스킬) 생성
- `record.md`의 후보 {n} **검증 결과**와 **되돌리기**가 채워짐
- 코드와 데이터가 원본 상태로 복원됨
- 진행 상태의 후보 {n} Phase 7이 ✅

### 실패 처리
- 측정 조건이 Phase 4와 달라졌는데 되돌릴 수 없으면, 비교 가능한 지표만 골라 해석하고
  나머지는 "조건 변경으로 비교 불가"로 명시한다.
- 되돌리기가 실패하면(`reset_ok`가 1이 아님) **다음 후보로 넘어가지 마라.** 데이터 상태를 먼저 복구한다.

> 다음 Phase 조건: 정합성 판정이 끝나고 코드와 데이터가 되돌려졌을 때
> → 계속하면 Phase 5 (후보 번호 +1) / 끝내면 Phase 8

> Skip 조건: 없음 (필수 Phase)
