# PR 작성 규칙

**PR 본문은 이력서와 경험 기술서의 소스로 쓰인다.**
Problem과 Solution만 읽어도 무엇이 왜 문제였고, 어떤 방법을 왜 골랐는지가 서술로 남게 쓴다.

## 제목

- 형식: `{type}: {설명}(#{이슈번호})`. 설명은 40자 이내 명사형
- 대상을 나열하지 말고 무엇을 해결했는지를 남긴다. 클래스명 나열과 괄호 중첩을 쓰지 않는다
  - (지양) `refactor: 게시글/댓글 작성 권한 검증 로직 분리 및 중복 제거(PostService/CommentService)`
  - (지향) `refactor: 작성 권한 검증 로직 중복 제거(#123)`

## 구조

- `.github/PULL_REQUEST_TEMPLATE.md`의 섹션 구조를 그대로 따른다. 템플릿의 HTML 주석은 넣지 않는다
- 섹션 제목은 `##`. 섹션 사이와 **굵은 소제목 블록 사이마다** `<br>`을 넣는다
  - 문제 1과 문제 2 사이, 해결 2와 해결 3 사이, 표와 다음 소제목 사이가 모두 해당한다
  - 표에 이름을 붙일 때는 굵게 쓰고 앞뒤에 `<br>`을 넣는다
  - 소제목 하나가 문단과 표를 여러 개 거느리면 그 안에서는 `<br>`을 넣지 않는다

| 섹션 | 쓰는 것 |
|---|---|
| PR Summary | 변경 사항 1~2문장. 여기서 전체 그림이 잡히게 한다 |
| Problem | 문제 상황과 원인. 그래서 무엇이 잘못되고 있었는지(영향)를 반드시 드러낸다 |
| Solution | 채택한 방법과 그것을 고른 이유. 핵심 클래스나 설정명은 필요할 때만 |
| Related Issue | `- close #{이슈번호}` |

- 문제가 여러 개면 번호로 나누고 Problem과 Solution의 번호를 1:1로 맞춘다 (`**문제 1 - ...**`, `**해결 1 - ...**`). 하나면 번호 없이 문단으로 쓴다

## 문체

- 존댓말(`~합니다`, `~했습니다`). 소제목은 명사형
- 가운데점 대신 콤마, 긴 대시 대신 짧은 대시
- 현업에서 통용되는 용어를 쓴다 (`전체 스캔` 대신 `풀스캔`, `술어` 대신 `WHERE 조건`)
- 영어를 옮긴 조어를 쓰지 않는다. 기준은 한국 개발자가 동료에게 말로 설명할 때 쓰는 단어다.
  영어가 더 흔하면 영어 그대로(fetch join, filesort, cache-aside, warm-up, TTL, fail-open), 나머지는 뜻이 통하는 한국어로 푼다

## 설계 결정 서술

- 선택지가 있었던 기법(캐싱, 락, 인덱스)은 결정을 나열하지 말고 이어지게 쓴다.
  순서는 왜 이 기법인가 → 무엇을 대상으로 → 어떻게(키, 갱신, 실패 시) → 그래서 무엇을 하지 않았나이고, 앞 결정이 뒤 결정의 전제가 된다
- 근거는 계획서, 측정 기록의 도입 근거와 설계 결정, 검토했지만 택하지 않은 안에서 가져온다
- 통용되는 기법 이름이 있으면 쓴다. 없으면 억지로 붙이지 않는다
- 깊이는 그 기법 자체의 선택까지다. 주변 장치(예외 핸들러 구조, 설정 클래스 배치)는 한 문장 이하
- 버린 안은 무엇을 왜 버렸는지 관측된 사실 한 줄로. 이유 없는 대안은 적지 않는다
- 서비스 특성에서 출발한 근거(트래픽 모양, 데이터가 바뀌는 때, 정합성 요구)를 기법보다 앞에 둔다. "빠르니까" 같은 일반론으로 정당화하지 않는다
- 여러 단계로 쌓인 개선은 앞 단계가 드러낸 문제를 뒤 단계가 받는 순서로 배치하고, 마지막에 단계별 추이를 한 줄로 붙인다 (`p95가 4,217 → 2,619 → 766 ms로 움직였습니다`)

## 금지

- 변경 파일과 메서드를 나열하지 않는다. diff가 보여준다
- 문단은 2~4문장. 작은 변경은 짧은 게 정상이다
- 커밋 메시지를 그대로 옮기지 않는다

## 성능 최적화 PR

수치가 값어치다. "빨라졌습니다"를 서술로만 쓰지 않는다.

1. 수치는 측정 기록(측정 결과 파일, 실행 계획, 부하 테스트 요약)에서 가져온다. 재지 않은 값은 추정하지 않고, 측정하지 않았다고 적는다
2. Before, After 수치는 표로 쓰고 **변화** 칼럼을 붙인다. 줄어드는 값은 퍼센트(`-99.2%`), 늘어나는 처리량은 배수(`19.3배`), 이미 퍼센트인 값은 퍼센트 포인트(`-77.3%p`)
3. 소제목 옆에 측정 기준을 괄호로 밝힌다 (`**내 게시글 조회 풀스캔** (게시글 2만 건, 회원 1천 명 기준)`)
4. 쿼리 개선이면 실행 계획 표(접근 방식, 사용 인덱스, 스캔 행, 반환 행, 실행시간)와 부하 지표 표(평균 실행시간, p95, p99, 처리량, 커넥션 풀 점유율)를 나눈다. 대상 쿼리가 여러 개면 쿼리별로 표를 나눈다
5. 인덱스를 추가했으면 정의를 한 줄로 먼저 적고, 컬럼마다 그 자리에 둔 이유를 문단으로 쓴다. 등호 조건과 범위 조건의 순서, 정렬을 인덱스로 푼 근거를 포함한다
6. 측정 조건(VU, duration, 데이터 규모)과 산출물 경로는 마지막 블록에 한 문단으로. 로컬 측정이면 하드웨어 의존성과 개선 판정 기준을 함께 적는다
7. 측정했지만 개선하지 않기로 한 대상도 근거 수치와 함께 남긴다
