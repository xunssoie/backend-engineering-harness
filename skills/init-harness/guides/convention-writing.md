# 컨벤션, 정책 문서 작성 기준

`/init-harness`가 문서 작성을 맡긴 서브에이전트가 읽는다. 대상 프로젝트의 코드를 읽고 아래 형식으로 쓴다.

## 공통 원칙

1. **관찰한 규칙만 쓴다.** 코드에서 반복되는 패턴이 근거다. 일반론(SOLID, 클린 코드 권고)이나 다른 프로젝트의 관례를 옮기지 않는다
2. **근거를 남긴다.** 규칙마다 그 패턴이 보이는 클래스 2개 이상을 떠올릴 수 있어야 한다. 한 곳에서만 보이면 규칙이 아니라 사례다
3. **혼재하면 쓰지 않는다.** 같은 상황에서 두 방식이 섞여 있으면 규칙으로 정하지 말고 "확인 필요"로 반환한다 (예: Builder와 팩토리 메서드가 반씩)
4. **짧게 쓴다.** 규칙은 한 줄 명령형("~한다", "~하지 마라"), 필요하면 이 프로젝트 코드에서 가져온 짧은 예시 하나. 예시는 실제 코드를 줄여 쓰고 클래스명은 그대로 둔다
5. **표기**: 한국어, 가운데점 대신 콤마, 긴 대시 대신 짧은 대시
6. **반환**: 작성한 파일 경로와, 근거가 부족해 쓰지 않은 "확인 필요" 항목(무엇이 어떻게 섞여 있는지 한 줄)을 반환한다

## 자동 로드 규칙 (`.claude/rules/`)

파일을 다룰 때 Claude Code가 자동으로 읽는다. 그래서 짧을수록 좋다. 파일 하나에 150줄을 넘기지 않는다.

```markdown
---
description: {무엇을 할 때 적용되는 규칙인지 한 줄}
paths:
  - "{이 규칙이 적용될 파일 glob, 실제 파일과 맞아야 한다}"
---

# {제목}

## {주제}

- {규칙}

```{언어}
{이 프로젝트 코드에서 줄인 예시}
```
```

| 파일 | 담는 것 | paths 예 |
|---|---|---|
| `project-structure.md` | 루트 패키지, 패키지 트리(도메인마다 한 줄 설명), 도메인 패키지 내부 구조, 레이어 흐름, 테스트 미러링 | 소스와 테스트 전체 |
| `code-convention/common.md` | 소스 위치, 레이어 의존 방향, 예외 처리(예외 클래스와 에러 코드 사용법), 객체 생성(팩토리, Builder), null 처리, 상수, 포맷팅, 네이밍, 주석, 로깅, 스프링 컴포넌트 선언 | 소스 전체 |
| `code-convention/{레이어}.md` | 그 레이어 고유의 패턴. controller(요청 매핑, 응답 형식, 인증 파라미터, 문서 인터페이스), service(트랜잭션, 검증 위치, 조회와 변경 분리), repository(쿼리 방식, 메서드 명명), domain(엔티티 선언, 연관관계, enum 매핑, 생성 규칙), dto(이름, 검증 어노테이션, 변환 메서드), facade(여러 서비스 조합 규칙) | `**/{레이어}/**` |
| `migration.md` | 마이그레이션 위치, 파일명 규칙(감지 결과의 style), 불변 원칙, SQL 스타일(테이블과 컬럼 명명, PK, FK, 시간 타입, enum, 인덱스 명명), 테스트 DB 호환 | 마이그레이션 디렉토리 |

## 필요할 때 읽는 문서 (`.claude/spec/`)

스킬이 필요할 때만 읽는다. frontmatter에는 `description`만 둔다.

| 파일 | 담는 것 |
|---|---|
| `git-convention.md` | 커밋 메시지 형식 `{type}: 내용(#이슈번호)`, 타입 표(타입, 용도, 이슈 라벨: `.claude/harness.json`의 types와 같은 표기), 제목 규칙(40자, 명사형, 대상 나열 금지), 표기 규칙, 브랜치 전략(감지 결과의 base, 보호 브랜치), 브랜치 명명 `{type}/{이슈번호}-{slug}` |
| `test-convention.md` | 테스트 종류(통합, 단위의 비중을 감지 결과의 counts로), 기반 어노테이션(감지된 커스텀 어노테이션), 네이밍, 의존성 주입, given/when/then, 예외 검증(예외 코드까지), Fixture 위치와 작성법, DB 전용 쿼리 테스트 |
| `api-docs-convention.md` | Swagger 문서를 어디에 두는지(Controller 직접, Docs 인터페이스), 인터페이스와 메서드 어노테이션, 에러 응답 예시 작성법, DTO 스키마 |
| `service-policy/README.md` | 작성 규칙(아래)과 도메인별 파일 표 |
| `service-policy/{도메인}.md` | 도메인의 비즈니스 규칙 |

`.claude/skills/write-test/template/test-code-template.md`는 이 프로젝트의 통합 테스트 한 벌과 Fixture 한 벌을 골격으로 만든다.
기존 테스트에서 가장 표준적인 것을 골라 자리표시자(`{Target}`, `{ERROR_CODE}`)로 바꾼다.

## 서비스 정책 작성 규칙

정책 문서는 코드를 읽지 않고도 서비스 규칙을 알 수 있게 하는 단일 출처다.

- **담는 것**: 사용자에게 드러나는 규칙과 판정 기준. 성공과 실패 조건, 제한 수치, 산정 기준, 검증 순서, 유효 기간과 초기화 시점, 권한 범위
- **담지 않는 것**: 클래스 구조, 파일 경로, 메서드 시그니처, 쿼리, 트랜잭션 처리
- 문장은 "무엇을 하면 무엇이 된다" 형태로 쓴다
- 위치 표기가 꼭 필요하면 `PostService:60` 수준까지. 파일 경로는 쓰지 않는다
- 정책이 없는 도메인도 파일을 두고 `- 별도 정책 없음`으로 남긴다
- 다른 도메인에 이미 적힌 정책은 옮겨 쓰지 않고 `{파일명}을 따른다`로 넘긴다
- **코드에서 읽은 초안이다.** 파일 첫머리에 `> 코드에서 추출한 초안이다. 의도와 다른 규칙이 있는지 검토가 필요하다.`를 둔다. 코드의 버그가 정책으로 굳지 않게, 의심스러운 동작은 규칙이 아니라 "확인 필요"로 반환한다

README의 갱신 규칙은 그대로 둔다: 코드 변경으로 규칙이 바뀌면 같은 작업에서 해당 도메인 파일을 고친다. write-plan은 계획 단계에서 읽고, implement는 구현 뒤 반영한다.
