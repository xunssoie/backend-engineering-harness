### 3-A. 데이터셋 (이슈 공용)

> 같은 이슈의 다른 대상이 채웠으면 3-B로 간다. 단, 이번 대상의 쿼리가 앞선 대상이 다루지 않은 테이블을 읽으면 그 테이블만 추가로 채운다.

1. 현재 행 수를 확인하게 한다. Phase 1에서 확정한 쿼리가 읽는 테이블만 다룬다.
   통계 뷰의 행 수는 추정치라 배 단위로 어긋난다. stacks 파일 **행 수** 절대로 실제 카운트를 쓴다.

2. 목표 규모를 호출자와 확정한다.
   - 앱 시드나 운영 통계가 있으면 그것이 운영 규모의 근사치다. 목표는 **운영 대비 배수**로 정하고,
     그 배수를 고른 이유(무엇을 관측하려는지)를 함께 확정한다. 배수가 클수록 적재, 워밍업, 버퍼 비용이 커지고
     운영에서 볼 일 없는 구간을 재게 된다. 근거 없는 큰 수를 받아들이지 마라.
   - 정렬, 집계, 윈도우 함수가 걸린 쿼리가 있으면 그 테이블의 목표를 개별 수치로 확정한다.
   - 데이터가 DB 버퍼보다 커지면 측정이 디스크 I/O를 잰다. 그 사실을 함께 확정한다.
   - 규모는 스킬이 정하지 않는다.

3. 목표 카디널리티를 호출자와 확정한다.
   - 대상 쿼리의 `WHERE`, `ORDER BY`, `GROUP BY` 컬럼마다 서로 다른 값의 개수를 정한다.
   - enum 성격의 컬럼은 **분포의 치우침**까지 정한다. 한 값에 몰린 분포와 균등 분포는 인덱스 선택도가 다르다.
   - 전문 검색이 대상이면 키워드당 매칭 건수를 정한다.
   - Phase 5-B가 이 값을 근거로 쓴다. 확정하지 않고 넘어가지 마라.

4. 인증이 필요한 대상이면 토큰 방식을 정한다 (`perf.tokens.mode`).
   - 기본은 **서명키로 직접 발급**(`mint-tokens.sh`, Phase 4에서 실행)이다. 로그인 API를 태우지 마라.
     로그인 SQL이 측정에 섞이고 수백 계정을 가입시키는 것보다 느리다.
   - **인증 필터가 DB를 보지 않고 대상 컨트롤러가 사용자 엔티티를 읽지 않으면 사용자 시드가 필요 없다.**
     토큰의 id가 사용자 테이블에 없어도 통과한다. 컨트롤러 시그니처와 필터를 먼저 확인하라.
   - **로그인 경로 자체를 측정할 때만** 실제 비밀번호 해시가 필요하다. 지어내지 말고 가입 API가 만든 값을 DB에서 읽어 쓴다.
     요청 형식은 프로젝트의 가입 DTO와 API 문서를 따른다. 해시는 `$`를 포함하므로 셸에서 가공하지 말고 `seeds.sql` 변수에 작은따옴표로 감싸 넣게 한다.

5. 목표에 미달하는 테이블이 있으면 시드를 만든다.
   - 프로젝트 시드 모듈(`seedModules`)에 필요한 테이블이 있으면 그 모듈을 쓴다. 없으면 `template/seeds/README.md`의 규칙대로
     `perf.seedsDir`에 **새 모듈을 만든다.** 실제 스키마(stacks 파일 **시드** 절의 필수 컬럼 조회)와 엔티티의 enum을 먼저 대조한다.
     새 모듈은 `perf.seedsDir/README.md`의 모듈 표와 변수 표에 추가한다. README가 없으면 만든다.
   - `.claude/resources/perf/{이슈번호}/seeds.sql`에는 **변수 블록만** 쓴다. 모듈 본문을 복사하지 마라. 실행할 때 `cat`으로 이어 붙인다.
   - 한 번만 쓸 테이블 블록은 `seeds.sql`에 직접 써도 된다. 두 번 이상 쓸 것 같으면 모듈로 만들자고 제안한다.
   - 모듈의 규모 상한을 넘는 규모면 README의 **대량 적재** 절차를 함께 제시한다.

     ```bash
     cat "$PERF_DIR/seeds.sql" "$SEEDS/{모듈}.sql" "$SEEDS/{모듈}.sql" | dbq
     ```

   - 모듈 말미의 검증 결과가 2, 3에서 확정한 값과 어긋나면 변수를 고쳐 다시 실행하게 한다. 어긋난 채로 넘어가지 마라.

6. 옵티마이저 통계를 갱신하게 한다. 빼면 첫 측정의 실행계획이 적재 전 통계로 잡힌다.

   ```bash
   perf_analyze {테이블...}
   ```

7. 확정한 규모(운영 대비 배수와 근거 포함), 카디널리티, 검증값, 시드 모듈과 변수를 `record.md`의 **측정 환경**에 적는다.

### 3-B. 부하 스크립트 (대상별)

1. `template/k6-script-template.js`를 Read하고 작성 규칙대로 `.claude/resources/perf/{이슈번호}/{슬러그}/test-script.js`를 만든다.
   `TARGET`은 슬러그, `ENDPOINT`는 경로, `AUTH_HEADER`와 `AUTH_PREFIX`는 `perf.tokens`의 값. 실행은 Phase 4에서 호출자가 한다.

2. 부하 조건(VU, duration, ID_START, USER_COUNT)과 캐시 상태를 호출자와 확정해 스크립트의 `CONDITION`과 `record.md`의 **측정 환경**에 적는다.
   - 같은 이슈의 다른 대상과 조건을 맞출지 확인한다. 다르면 대상 간 비교가 불가능하다.
   - VU 상한은 커넥션 풀 크기와 함께 본다. 풀보다 훨씬 큰 VU는 쿼리가 아니라 커넥션 대기를 잰다.
   - ID_START와 USER_COUNT는 시드가 실제로 만든 id 범위와 일치시킨다. 기본값을 그대로 두지 않는다.
   - 이후 값이 바뀌면 변경값과 시점을 덧붙인다. 기존 값을 덮어쓰지 마라.

3. **쓰기 엔드포인트면 되돌리기 SQL을 여기서 확정해 `record.md`에 적는다.** Phase 4와 8이 같은 자리에서 실행한다.
   쓰기는 행을 남기고 집계 컬럼을 바꾼다. 유니크 제약이 있으면 되돌리지 않을 때 2회차부터 전부 중복 실패다.

   > 예시 (수강신청 프로젝트): 신청 행을 시드 회원 범위로 지우고, 강의의 현재 인원 컬럼을 0으로 되돌린다.
   >
   > ```sql
   > DELETE FROM {신청 테이블} WHERE {회원 id 컬럼} BETWEEN {시작} AND {끝};
   > UPDATE {강의 테이블} SET {인원 컬럼} = 0 WHERE id BETWEEN {시작} AND {끝};
   > ```

### 출력
- 새 시드 모듈 (필요한 경우), `seeds.sql` (필요한 경우), `test-script.js`
- `record.md`의 **측정 환경**에 규모와 근거, 카디널리티, 부하 조건, 캐시 상태, 되돌리기 절차
- `harness perf-progress {record.md} --phase 3 --mark ✅` (둘 다 건너뛰면 ⏭️)
