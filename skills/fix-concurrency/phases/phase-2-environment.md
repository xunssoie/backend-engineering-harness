## Phase 2. 측정 환경 점검

### 목적
경합을 왜곡 없이 관측할 수 있는 상태인지 확인한다.
**게이트.** 아래 다섯 항목 중 하나라도 통과하지 못하면 Phase 3으로 넘어가지 마라.
환경이 어긋난 채로 잰 값은 경합이 아니라 환경을 잰 값이다.

### 선행 조건
- Phase 1 완료
- `.claude/harness.json`의 `perf` 절에 DB 접속 설정(`db`, `dbContainer`, `dbName`, `dbUser`, `appBaseUrl`)이 있다.
  주입된 `stack`이 null이면 이 절부터 채우게 하고 멈춘다
- DB가 떠 있다

### 참조 파일
- 주입된 `stack` (`stacks/mysql.md` 또는 `stacks/postgresql.md`)
- `.claude/skills/fix-concurrency/template/application-conc.yml` (Spring Boot 예시)

### 절차

1. **측정 프로파일을 준비한다.**
   `concurrency.profileFile`이 없으면(`profileFileExists`가 false) 프로젝트의 기본 설정과 `template/application-conc.yml`을 Read해
   그 원칙대로 생성한다. 이미 있으면 만들지 말고 현재 값을 읽어 아래 점검에 쓴다.

   - 이 파일은 `.gitignore` 대상이 아니다. 측정 조건이 기록으로 남아야 후보 간 비교가 성립한다.
   - **성능 측정용 프로파일을 복사해 쓰지 마라.** 커넥션 풀 크기 규칙이 정반대다.
     perf는 실사용에 가까운 풀을 쓰지만 conc는 부하 VU 이상으로 키운다(5번 참조).
   - 기동 명령, 포트, 헬스 URL이 프로젝트와 다르면 `.claude/harness.json`의 `concurrency` 절을 고치게 한다.

2. **애플리케이션을 띄우도록 제시한다.** 실행은 호출자가 한다.

   ```bash
   bash .claude/skills/fix-concurrency/template/restart-app.sh
   ```

   - `restart-app.sh`는 포트를 점유한 기존 프로세스를 먼저 내리고, 기동과 헬스 확인,
     커넥션 풀 충전까지 한 번에 처리한다. **기동 명령을 맨손으로 제시하지 마라**
     (이유는 `phase-6-apply.md` 5번을 보라).

3. **기동 확인.** `restart-app.sh`가 `재기동 완료.`로 끝났는지 받는다.
   - `!! 기동 실패`로 끝났으면 출력된 로그를 받아 원인을 짚는다. 다음 항목으로 넘어가지 마라.

4. **인증 경로 확인.** 측정용 토큰을 **로그인 API로 받지 않는다.**

   - 시드 사용자의 비밀번호는 해시가 아닌 더미 값이라 로그인 대조를 통과하지 못하고,
     수백 개 계정을 가입 API로 만드는 것도 측정 준비에 맞지 않는다.
   - 그래서 측정용 토큰은 Phase 3에서 `.claude/scripts/perf/mint-tokens.sh`로 서명키에서 직접 만든다.
     여기서는 측정 프로파일에 서명키가 있는지, 서버가 토큰을 어느 헤더에서 읽는지만 확인한다.
   - 헤더 이름과 접두어가 `perf.tokens.header`, `perf.tokens.headerPrefix`와 다르면 설정을 고치게 한다.
   - 서명 방식이 `mint-tokens.sh`와 맞지 않으면(알고리즘, subject, 필수 클레임) 그 차이를 보고한다.

5. **커넥션 풀 크기를 확인한다.** 이 항목이 동시성 측정에서 가장 자주 틀어진다.

   - 측정 프로파일의 풀 최대 크기와 최소 유휴 값을 읽는다.
   - **풀 크기가 부하 VU보다 작으면 락 경합이 아니라 커넥션 대기를 재게 된다.**
     Phase 3에서 정할 VU 이상으로 잡는다. VU를 아직 안 정했으면 Phase 3에서 정한 뒤 이 항목으로 돌아온다.
   - DB의 최대 접속 수가 풀 크기보다 작으면 풀이 차지 않는다. `stack`의 **격리 수준과 타임아웃** 절로 확인한다.
   - 풀이 설정대로 바인딩되는지 확인한다. 데이터소스를 직접 정의한 프로젝트는 풀 설정 키가 바인딩되지 않는 경우가 있다.
     `concurrency.poolMinIdle`을 최소 유휴 값으로 두면 `restart-app.sh`가 실제 DB 접속 수로 확인한다.
   - 값을 바꾸면 `record.md`의 **측정 환경**에 변경 시점과 함께 남긴다.

6. **격리 수준을 확인해 기록한다.** `stack`의 **격리 수준과 타임아웃** 절의 명령을 제시한다.

   - 낙관적 락의 재시도 빈도, `FOR UPDATE`의 범위, 동시 UPDATE의 재평가 방식이 여기에 달려 있다.
   - **락 대기 타임아웃이 부하 지속시간보다 길면** 비관적 락 후보에서 요청이 타임아웃 없이 끝까지 밀린다.
     그 상태로도 측정은 되지만, 실패가 관측되지 않는 이유가 되므로 값을 기록해둔다.

7. **락 관측 수단을 점검한다.** `stack`의 **락 관측 수단 점검** 절의 명령을 제시한다.
   여기서 값이 안 나오면 Phase 4, 7에서 2급 지표를 채울 수 없다.

   - 꺼진 지표가 있으면 같은 절의 방법으로 켜도록 제시한다.
   - 실시간 락 관측이 권한 오류로 실패하면 그 사실을 기록하고 `concurrency.sampleLockWaits`를 false로 둔다.
     누적 카운터만으로도 후보 비교는 성립한다.

8. 확인한 값을 `record.md`의 **측정 환경**에 채우고 진행 상태를 갱신한다.

   ```bash
   harness conc-progress {record.md 경로} --phase 2 --mark ✅
   ```

### 출력
- 측정 프로파일(`concurrency.profileFile`) 준비
- `record.md`의 **측정 환경**에 풀 크기, DB 최대 접속 수, 격리 수준, 락 대기 타임아웃, 관측 가능한 락 지표가 기록
- 진행 상태의 Phase 2가 ✅

### 실패 처리

| 증상 | 처리 |
|---|---|
| 컨텍스트 기동 실패 | 기동 로그를 받아 원인을 짚는다. DB 미기동과 마이그레이션 실패가 흔하다 |
| 락 카운터가 전부 비활성 | `stack`의 방법으로 켜고 재확인. 안 되면 읽히는 지표만으로 진행하고 기록 |
| 실시간 락 관측 불가 | 표본 수집을 끄고 진행. `record.md`에 명시 |
| 풀 크기를 VU 이상으로 못 올림 | 그 상한을 VU 상한으로 삼는다. 풀보다 큰 VU로 재지 마라 |
