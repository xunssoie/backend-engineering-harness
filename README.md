# backend-engineering-harness

이 하네스는 세 가지로 움직여요.

- **스킬**이 흐름을 이끌어요. "이슈 열어줘", "커밋해줘"라고 하면 정해진 순서대로 진행해요.
- **CLI**가 반복 작업을 맡아요. 브랜치와 이슈 정보 모으기, 커밋 메시지 검사, 테스트 기록처럼 매번 똑같은 일이에요. Claude는 판단에만 집중해요.
- **훅**이 위험한 명령을 막아요. force push나 배포된 마이그레이션 수정은 실행 전에 막거나 한 번 더 물어봐요.

<br>

### 바로 시작하기
---
준비물은 Git, Python 3, jq, GitHub CLI예요. `gh auth login`은 미리 해 두세요. jq가 없으면 안전장치가 돌지 않아 명령 실행과 파일 수정이 막혀요. Docker는 테스트가 필요로 할 때, k6는 성능 개선, 동시성 개선 스킬을 쓸 때만 있으면 돼요.

```bash
# 1. 프로젝트 루트에서 .claude로 클론해요
git clone https://github.com/xunssoie/backend-engineering-harness.git .claude

# 2. Claude Code를 열고 프로젝트에 맞게 설정해요. 끝나면 .claude를 커밋해요
/init-harness

# 3. 할 일을 말해요. 이슈 → 계획 → 구현 → 테스트 → 커밋 → PR → 리뷰 반영 순서로 진행해요
/dev-pipeline 로그인 실패 시 리다이렉트 경로 수정

# 중간까지만 할 때, 세션을 새로 열어 이어갈 때
/dev-pipeline 커밋까지
/dev-pipeline
```

`/init-harness`는 빌드 파일, 소스 구조, 마이그레이션, 브랜치, 라벨을 살펴보고 알아낼 수 없는 것만 물어봐요. 끝나면 설정과 컨벤션 문서 초안이 생기는데, 코드에서 근거를 찾은 규칙만 담아요. 애매한 항목은 **확인 필요** 목록에 모아 두니 한 번 훑어보고 채워 주세요.

`/dev-pipeline`에 넘기는 할 일은 최대한 자세히 적어 주세요. 어디를 어떻게 바꿀지 분명할수록 되묻는 횟수가 줄고, 같은 결과를 더 적은 토큰으로 얻어요.

<br>

### 스킬
---
단계마다 스킬이 하나씩 있어요. `/` 명령으로 불러도 되고, "커밋해줘"처럼 말해도 돼요.

**개발 파이프라인**

| 스킬 | 하는 일 |
|---|---|
| `/dev-pipeline` | 아래 단계를 지금 위치부터 끝까지 이어서 진행해요 |
| `/open-issue` | 할 일을 대화로 정리해 GitHub 이슈를 열고 브랜치를 만들어요 |
| `/write-plan` | 이슈를 읽고 어떤 클래스의 어떤 메서드를 어떻게 바꿀지 계획서를 써요 |
| `/implement` | 계획서대로 구현해요 |
| `/write-test` | 테스트를 쓰고 실행해요 |
| `/commit-push` | 변경을 작업 성격별로 나눠 컨벤션에 맞게 커밋하고 push해요 |
| `/open-pr` | PR 본문을 쓰고 라벨과 담당자를 지정해 PR을 열어요 |
| `/review-feedback` | 리뷰 봇 피드백을 코드와 대조해 상·중·하로 판정하고, 고른 것만 고쳐요 |

<br>

**성능과 동시성 문제 해결**

DB를 쓰는 프로젝트라면 `/init-harness`에서 켤 수 있어요. 어떤 기법을 쓸지는 사용자가 정하고, 부하 테스트도 사용자가 직접 실행해요. 스킬은 실행할 명령을 알려 주고 결과를 정리해요.

| 스킬 | 하는 일 |
|---|---|
| `/optimize-performance` | 느린 API를 측정해 병목과 개선 기법을 근거와 함께 보여 줘요 |
| `/fix-concurrency` | 동시 요청에서 깨지는 규칙을 재현하고, 제어 기법을 하나씩 적용해 비교해요 |

<br>

**하네스 관리**

| 스킬 | 하는 일 |
|---|---|
| `/init-harness` | 하네스를 프로젝트에 맞게 설정해요. 설정을 바꾸고 싶을 때 다시 실행해도 돼요 |
| `/update-harness` | 새 버전으로 업데이트해요. 프로젝트에서 고친 파일은 양쪽 변경을 합쳐요 |

<br>

그 밖에 `/conversation-feedback`을 부르면 지금까지 나눈 대화를 돌아보고 성장에 도움이 되는 피드백을 줘요. 스킬 안에서만 쓰는 서브에이전트(`commit-planner`, `pr-writer`, `feedback-judge`)도 들어 있는데요, 직접 부를 일은 없어요.

<br>

### 안전장치
---
Claude가 실수로 되돌리기 어려운 일을 하지 않도록 훅이 지켜요.

- **막아요**

    force push, `git reset --hard`, Docker 컨테이너와 이미지 삭제, `flywayClean`, 프로젝트 루트나 홈 디렉토리 삭제

- **한 번 더 물어봐요**

     소스 파일 삭제, `git clean`, `--force-with-lease` push, DB의 `DROP`과 `TRUNCATE`, `chmod 777`

- **배포됐을 수 있는 마이그레이션은 못 고쳐요**

     기준 브랜치(기본값 `origin/main`)에 이미 있는 Flyway 파일이 대상이에요. 지금 브랜치에서 만든 파일은 자유롭게 고쳐도 돼요

- **테스트는 하네스로 돌려요**

     Docker 확인, 로그 보관, 결과 집계를 같이 하기 위해서예요. 빌드 도구로 직접 돌리면 막히니, 컴파일만 볼 때는 `-x test`를 붙여요

- **하네스 자신도 지켜요**

     훅, 권한, 하네스 설정을 바꾸려면 사용자 승인이 필요해요

<br>

### 업데이트
---
새 버전이 나오면 세션을 시작할 때 알려 줘요. `/update-harness`를 실행하면 변경 기록과 바뀔 파일을 먼저 보여 주고, 진행할지 물어봐요. 프로젝트에서 고친 파일은 양쪽 변경을 합치고, 충돌이 나면 두 버전을 비교해 보여 줘요. 설치할 때 뺀 스킬은 다시 생기지 않아요.

<br>

### 프로젝트에 맞게 다듬기
---
설치가 끝나면 `.claude`는 프로젝트 파일이에요. 컨벤션이나 정책이 바뀌면 바로 고쳐 쓰면 되고, 고친 내용은 업데이트해도 유지돼요.

```
.claude/
├── CLAUDE.md        Claude가 읽는 하네스 안내
├── harness.json     파이프라인 단계, 확인 지점, 테스트 명령
├── rules/           프로젝트 구조, 코드 컨벤션, 마이그레이션 규칙
├── spec/            Git과 테스트 컨벤션, PR 작성 규칙, 서비스 정책
├── skills/          스킬
├── agents/          스킬이 쓰는 서브에이전트
├── hooks/           안전장치
└── scripts/         하네스 CLI
```

단계나 확인 지점을 바꾸고 싶다면 `/init-harness`를 다시 실행하세요. 지금 값을 기본으로 보여 주고 바꿀 것만 물어봐요.
